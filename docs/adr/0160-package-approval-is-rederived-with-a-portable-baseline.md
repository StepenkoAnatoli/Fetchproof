# ADR-0160 - Package approval is re-derived with a portable baseline

- **Date:** 2026-10-13
- **Status:** accepted
- **Area:** artifact approval derivation and validation
- **Refines:** ADR-0032; retains ADR-0069 and ADR-0138 compatibility
- **Defect:** #357, qualified gap-audit rank 2

## Evidence

The [decision research](../decisions/2026-10-13-portable-artifact-authorization/research/BRIEF.md)
has nine pinned first-party source captures and a verified ledger. Its three unknowns
are closed and its own preflight passes. The retained profile probe uses explicitly
synthetic passing corpora with the actual historical writer at
`3bac1f26ddbf8cb6a794626e53dc2af313860940`, plus the current writer at `3fa03fa`.
These are historical-format fixtures generated by those real writers, not archived user
corpora. Both the unstamped and early-stamped writer outputs are format 1.0.0 and claim
approval. The early stamp's historical input hash matches its covered inputs but differs
from the current hash; applying only current producer currency rules rejects that valid
historical profile. The current writer's stamp explicitly contains `gate=unknown` while
the early one has no gate field, even though `draftStamp` reports unknown for both.

## Decision

- Move the existing approval derivation to one shared module so the producer and
  validator use the same gate, map, findings and authored-brief rules without an import
  cycle. The producer keeps its current API and machine-specific preflight behavior.
- For a package claiming approval, the validator materializes the already checked
  project bytes and re-derives approval with an explicit portable context. It uses the
  shared unpromoted pluralist findings and default 180-day freshness horizon, never
  consumer policy, hooks or overrides. Report that baseline and its warning findings.
- A package declaring authorization false is never upgraded. Invalid bytes, schema or
  provenance still prevent approval before any derivation can authorize a build.
- Current matching stamps retain their normal currency check. Authored unstamped
  briefs retain ADR-0138's approval path with unknown currency disclosed.
- Only format major 1 may use pre-0069 stamp compatibility: the last valid literal
  marker must have no gate field, and its inputs must match the exact historical hash
  over topic, intent, unknowns and evidence rows. Report this compatibility explicitly.
  Current gate, map, findings and authored-section checks still run on that corpus.
  A mismatch in the historical covered inputs is not accepted, and an explicit
  `gate=unknown` marker does not qualify as a missing-field legacy marker.
- Resolve a blank Raw cell through `captureOf`, as the shared corpus resolver does.
  An unresolved or unreadable row is not reviewed; extractor-identical findings remain
  negative evidence of an unreviewed row. This does not grade semantic correctness.

## Rejected alternatives

- **Use the consumer's normal preflight context.** The manifest carries neither the
  producer's strict policy nor its custom freshness horizon; a consumer policy or hook
  cannot establish the producer's exact verdict and makes authorization nonportable.
- **Reject every old input hash.** The actual historical writer probe produces a valid
  early approval that fails that test solely because ADR-0069 expanded the hash.
- **Ignore all historical stamps.** Comparing the historical covered inputs preserves
  a check that would otherwise disappear; current and legacy mismatches remain refusals.
- **Compare false claims to an approving derived state and upgrade them.** A conservative
  producer declaration remains conservative; the validator cannot supply approval the
  incoming package explicitly withheld.

## Consequences and trigger

No package format or public CLI option changes. The result's existing warning channel
discloses the portable baseline and legacy compatibility. This checks consistency with
the packaged corpus rather than establishing who reviewed it; ADR-0032's self-attested
provenance and ADR-0013's semantic-review boundary remain in force. A future format with
an explicit policy or a new stamp profile must define its own derivation/compatibility
rules before this legacy exception is extended beyond major 1.
