# Researcher reliability and research-quality review

Date: 2026-09-16. Review target: `C:\Users\PC\Desktop\FreeBuff\Deep-Research-Agent-main`.

## Verdict

**This machine is authenticated, but the researcher is not ready for dependable end-to-end use.** The earlier unconditional “yes” was not supported by a collection test. Its Windows Firecrawl adapter rejects the temporary output paths generated by every search, scrape, and map operation. Doctor and `--status` do not exercise that path, so both can look healthy while collection cannot start.

The project has a useful architecture: explicit research questions, cached sources, a verifiable ledger, and a shared gate. However, it currently protects provenance more effectively than research quality. The supplied corpus passes preflight while its brief still contains TODO decisions and some findings do not answer the questions they supposedly close. Several output-generation defects can also erase reviewed decisions or distribute stale findings.

This report contains suggestions only. No product fixes, configuration changes, installs, or commits were deliberately made. A defect in the existing test suite did invoke the installer against the real user installation; that incident and its uncertainty are documented below. The review added this report and a separate reproduction script.

## What this project actually does

This is a Node command-line research toolkit driven by a person or an AI agent. The toolkit does not itself make model calls to reason about sources or produce a fully reviewed synthesis. `firstFinding()` is a text-scoring heuristic; an agent must replace its draft findings with claims that answer the research questions.

| Stage | Actual code path | Result and responsibility |
|---|---|---|
| Establish scope | Agent reads instructions and states intent | Human/agent chooses what “done” means. |
| Decompose | `bin/decompose.mjs → lib/decompose.mjs → transport` | Searches/maps sources, collects a few pages, seeds nine universal dimensions in `MAP.md`. The agent marks coverage. |
| Contract | Agent writes `DISCOVERY.md` and `plan.json` | Blocking unknowns and planned collection. |
| Collect | `bin/research.mjs → research-run.mjs → collect.mjs` | Chooses URLs, applies a scrape budget and local cache, calls the selected adapter. |
| Persist | `collect.mjs → corpus.mjs / provenance.mjs` | Writes a raw capture, hashes it into the ledger, adds evidence and source rows. |
| Evaluate | `preflight.mjs → corpus.mjs + checks.mjs` | Checks structure, links, hashes, age, source labels, closure, and coverage. It does not establish whether a claim follows from its source. |
| Deliver | `brief.mjs / audit.mjs / archive.mjs` | Generates a draft brief, versioned audit documents, and ZIP attachments. Judgement still needs review. |
| Enforce | Git pre-commit hook and edit hook | Calls the gate. Effectiveness depends on the actual Git checkout, runtime integration, and chosen policy. |

The collector machine produces evidence. A builder machine should consume it and run handoff verification. Configuration defaults to `collector`, `failOpen: true`, edit mode `ask`, and evidence policy `pluralist`.

## Confirmed findings and suggested remedies

Severity: P0 = current core workflow blocked; P1 = significant integrity, data-loss, security, or enforcement defect; P2 = correctness/reliability issue. “Reproduced” means observed with local execution. “Code-traced” means the path is present in the code, with the stated runtime scenario not independently reproduced.

### F01 — P0: ordinary Windows collection never launches

**Reproduced.** `firecrawl.mjs:84,304,413`: the adapter appends `-o` followed by a Windows temporary path containing backslashes. `CMD_SAFE_ARG` excludes backslashes. Search, map, and scrape each returned `ok:false`; the injected spawn count stayed zero even for `https://example.com`. Status/version work because they do not use an output file.

Suggestion: use a transport invocation that preserves argument boundaries without the `.cmd` interpreter, such as a verified Node CLI entry point or an API adapter. A smaller interim fix could support trusted generated output paths, but merely relaxing the regular expression needs careful shell tests. Preserve the original shell-injection protections. Require actual collection-path smoke tests before reporting “ready.” ADR-0020 would need a superseding decision if its invocation strategy changes.

### F02 — P1: tests can deploy into the real user installation

**Reproduced and observed in the suite.** `test/install.test.mjs:34` isolates HOME only; `bin/install.mjs` resolves its deployment from `os.homedir()`. Git tests also inherit real global configuration. See the incident above.

Suggestion: inject every machine path or run tests in a disposable OS user/container, explicitly isolating Windows USERPROFILE, Git configuration, kit config/state, and runtime roots. Add a containment assertion before any installer writes. Test setup should report missing shell prerequisites instead of collapsing spawn errors into assertion failures.

### F03 — P1: the advertised keyless fallback cannot pass provenance

**Reproduced.** `http-transport.mjs:263` returns successful scrape results without a `command`. `collect.mjs` writes that as `command: undefined`. `checks.mjs:163` requires the command text to contain `firecrawl`, regardless of the actual named transport. A successful keyless-shaped capture was collected, then rejected with `capture-command`, even under pluralist policy.

Suggestion: define and validate a common transport result contract, and judge provenance by the recorded adapter and supported operation. Fabricating a Firecrawl command for HTTP captures would make the record less honest.

### F04 — P1: keyless extraction drops content and labels it complete

**Reproduced end to end.** `http-transport.mjs` chooses the largest matching HTML block, discards sibling blocks, then labels output `full` solely when it has at least 1,500 characters. A local two-section page returned 4,319 characters and `full` while omitting the shorter section containing the critical quota exception. Headings, lists, and links can also disappear because the selected block has already had tags stripped before markdown conversion.

Suggestion: preserve meaningful page sections and links with a document parser; record extraction limitations. Completeness must be assessed against the needed sections, not length. Firecrawl's unconditional `full` stamp also needs a narrower definition: extracting main content is not proof that a particular claim's supporting section arrived.

### F05 — P1: rerunning the brief generator destroys reviewed edits

**Reproduced.** `brief.mjs:139,258` treats any document retaining “Auto-drafted” as a replaceable draft, even after someone edits it. Adding a reviewed conclusion, then calling `writeBrief()` without force returned `wrote:true` and deleted the added text. The generated instructions explicitly promise the opposite. A retained template marker has the same ownership problem.

Suggestion: default to preserving existing content, generate to a separate draft, or track the exact prior generated bytes and refuse when they differ. A marker identifies origin, not whether a document remains unedited.

### F06 — P1: changed research does not refresh its audit

**Reproduced.** `audit.mjs:59,469` fingerprints evidence IDs/dates/paths and unknown/map status links, but excludes finding text, intent, question text, the brief's decisions/contradictions, and other displayed content. Editing a claim and the brief still returned `reason: unchanged`.

Suggestion: fingerprint all canonical inputs that affect the output, including reviewed brief sections and relevant failure/provenance records. Make the dependency set explicit and test a change to each input.

### F07 — P1: unknown review state becomes an affirmative completion claim

**Reproduced; live corpus affected.** `audit.mjs:411` renders a missing/TODO contradictions section as “No contradictions were flagged.” `brief.mjs:202` announces research complete while emitting TODO decision sections. The gate permits a missing brief, empty plan file, and empty findings; all passed isolated probes. Missing or unmarked topic maps are warnings by design, also allowing PASS.

Suggestion: distinguish three states: corpus structurally valid, research reviewed, and handoff approved. Preserve “not reviewed” as a visible status. Do not render primary-source or independent-agreement assurances unless those properties were checked. A separate release/handoff check avoids preventing collection while still blocking premature handoff.

### F08 — P1: the commit gate validates different content from the commit

**Reproduced.** `gate.mjs:193` reads the working-tree corpus, while Git supplies only staged filenames. A fixture staged an OPEN discovery contract, then restored CLOSED only in the working tree. With staged source and architecture files, the gate returned exit 0 although `git show :research/DISCOVERY.md` still contained OPEN.

Suggestion: evaluate an index snapshot for commit checks, or explicitly reject relevant staged/working-tree divergence. Continue evaluating the working tree for interactive research checks.

### F09 — P1: deleted and quoted paths escape parts of commit enforcement

**Code-traced.** `githooks/pre-commit:140,157` filters to ACMR, excluding deletions and type changes. A deletion-only change can exit before gate evaluation. The hook also emits non-NUL names, so Git's quoted unusual/non-ASCII paths can fail the literal code-prefix comparison and evade the architecture-map rule. This does not imply every Unicode filename bypasses the entire research verdict.

Suggestion: include relevant deletion/type-change statuses and pipe NUL-delimited filenames into the already NUL-capable reader. [Git's documentation](https://git-scm.com/docs/git-diff) confirms the quoting behavior and the `-z` format. The existing triage description that a newline filename necessarily becomes multiple lines is imprecise: Git normally quotes it; the prefix mismatch is the concrete issue.

### F10 — P1: a supplied audit manifest can package files outside the project

**Reproduced with synthetic data.** `audit.mjs:651,669` resolves a manifest filename without enforcing containment in `research/audits`. A `../../../private-canary.txt` entry successfully bundled a harmless file outside the fixture project. `path.basename()` sanitizes the ZIP entry name only after the unrestricted source read.

Suggestion: validate manifest schema, constrain both input and output paths, reject traversal/absolute paths, and check resolved real paths for symlink escapes. This matters when a corpus/manifest arrives from another machine and the operator asks for a ZIP. No real private file was read or packaged in the reproduction.

### F11 — P1: evidence IDs collide and silently change reference meaning

**Reproduced.** `collect.mjs:171` uses row count plus one rather than the highest existing ID. With E-01 and E-03 present, the next collection creates a second E-03. `corpus.mjs:696` builds a Map that silently selects the last duplicate; preflight still passes. The source-ID allocation has the same count-based pattern at `collect.mjs:187`.

Suggestion: use the existing `nextId()` helper or stable unique identifiers, and reject duplicate evidence/unknown/source IDs before building indexes. This is about preserving citation meaning, not cosmetic numbering.

### F12 — P1: resuming collection can make a recoverable ledger tail unrecoverable

**Reproduced.** `provenance.mjs:122` reads ledger entries but ignores parse problems before appending. After a truncated tail, it appends a valid JSON object onto that unfinished line. The combined malformed line now ends in a newline; `repairLedgerTail()` refuses to remove it. The probe returned `repaired:false` and a malformed ledger row.

Suggestion: validate ledger state under the write lock before any append. Refuse with a precise recovery instruction or perform only a verified tail repair. Never spend on new collection before establishing that its result can be recorded safely.

### F13 — P1: lock recovery mishandles abandoned and long-running holders

**Reproduced predicates and acquisition behavior.** `provenance.mjs:446` declares even a live PID stale after ten minutes; `runResearch()` can hold the lock across many slow requests. A contender can therefore enter during a valid long run. Conversely, `acquireLock():479` never sends an unidentifiable holder to the age check: an eleven-minute-old empty lock still timed out instead of being recovered.

Suggestion: use a single-writer model or a lock/lease with explicit liveness and heartbeat semantics. Age alone must not evict a live writer; abandoned empty locks need bounded recovery. The final compare-then-unlink also remains a race window, which this review identified by inspection rather than a stress reproduction. Current ten-minute policies are documented decisions, so changing them should supersede the relevant ADR explicitly.

### F14 — P1: phase zero bypasses the full collection critical section

**Code-traced.** `decompose.mjs:251` calls `collectOne()` without the run-level lock used by `research-run.mjs:239`. `appendFetch()` locks only the ledger operation; raw naming/writes and evidence/source read-modify-writes happen outside it. Concurrent decomposition and collection can lose table updates or race on filenames/IDs even if individual ledger appends serialize. Research also loads its raw cache index before acquiring the run lock, allowing a stale cache decision after another collector finishes.

Suggestion: put the complete durable one-page operation under one shared writer boundary, including fresh cache lookup, ID allocation, capture publication, ledger and row updates. Do not infer full transaction safety from a ledger-only lock. Concurrent data loss was not stress-tested in this review.

### F15 — P1: a corrupt audit index destroys the “immutable” guarantee

**Reproduced.** `audit.mjs:42` treats invalid JSON as an empty index. The next `writeAudit()` starts at v0.1 again and overwrites a same-day v0.1 file. In the fixture the pathname was unchanged and the bytes changed.

Suggestion: distinguish absent index from corrupt index, refuse corruption, use atomic index publication and exclusive creation for immutable output files. Recovery should rebuild a proposed manifest from verified existing audits, with explicit review.

### F16 — P1: an unreadable role config can enable collection

**Reproduced.** With corrupt config and no last-good snapshot, `machine.mjs:276` tightens only `failOpen`. `machineRole():336` still returns collector and `collectionPolicy()` returns `mayCollect:true`. The “every config was previously snapshotted” rationale does not cover hand-created configs, copied machines, denied snapshot writes, or missing backups.

Suggestion: retain a distinct unknown role/config state and refuse metered collection until it is resolved. Validate field values too; syntactically valid misspellings should not silently relax role or policy.

### F17 — P1: hook installation/removal can remove unrelated hooks

**Reproduced with dry-run output.** `installer.mjs:153–155,197` removes whole hook groups if any command mentions this kit's hook. A group containing both `edit-gate.mjs` and an unrelated check loses the unrelated check during installation. Removal has the same group-level filtering.

Suggestion: modify only recognized individual hook entries, preserve other commands and group settings, and remove a group only if it becomes empty. Keep unique backups for each actual settings mutation.

### F18 — P2: audit contents always use the default version

**Reproduced.** `audit.mjs:467–472,490–497` renders before calculating the next version and does not re-render with that version. A filename/index at v0.2 contains `version: 0.1` and an H1 saying v0.1. Parent links in subtopic documents can also misidentify the intended main snapshot.

Suggestion: resolve versions before rendering and pin parent/sibling references to the actual bundle snapshot. Verify filename, metadata, title, manifest, and references agree.

### F19 — P2: dry-run changes project state and misrepresents the budget

**Reproduced.** `research-run.mjs:127` creates `research/raw/` even during dry-run, making a previously ungated directory gated. Its dry-run branch never increments attempted scrapes: two explicit URLs with a cap of one print two scrape commands.

Suggestion: make planning a pure computation and render the same budget/cache decisions execution would take. Preview and execution should consume the same candidate plan.

### F20 — P2: decomposition can succeed without material, ignore invalid budgets, and refuse its own draft

**Reproduced.** `decompose.mjs` writes a map even when all searches fail, omits their error messages, and the CLI returns success. A NaN scrape cap is accepted and does not cap attempts; the CLI converts arbitrary text with `Number()` without validation. A fresh seeded map has nine rows, so the next run rejects it as filled even though all statuses remain blank.

Suggestion: validate numeric flags before any request, preserve adapter failures, report empty/failed gathering distinctly, and distinguish an untouched generated map from authored coverage. Require explicit acceptance for an intentionally material-free decomposition.

### F21 — P2: refresh does not resolve stale citations or prove upstream freshness

**Reproduced stale-row case; cache behavior code-traced.** A forced refresh appends E-02 but leaves old E-01 and its unknown references intact. `checks.mjs:125` fails every stale evidence row, including the old one, so the suggested refresh does not clear the blocker. Separately, Firecrawl `cacheState` and `cachedAt` are normalized then discarded, while every new capture gets the current retrieval time; no upstream freshness option is propagated by this kit.

Suggestion: preserve old captures as history, explicitly supersede/review active citations, and distinguish retrieved-at from source-fetched-at. A refresh must trigger claim review, not silently substitute a new page beneath an old assertion. Firecrawl documents upstream caching and an explicit `maxAge: 0` fresh-fetch control; that capability must be verified against the pinned adapter version before integration. [Firecrawl scrape documentation](https://docs.firecrawl.dev/features/scrape#caching-and-maxage).

### F22 — P2: table writers violate the reader's header-order contract

**Reproduced.** The parser accepts reordered headers, but `appendRow()` inserts values in caller order into any existing header layout, and `upsertRow()` also writes canonical order. With URL and Retrieved moved, collection produced a URL cell containing today's date, a retrieval cell containing `P`, and type `H` from the URL. See `corpus.mjs:766,789`.

Suggestion: map values to the existing normalized header order, or refuse unsupported headers before writing. Pin both reader/writer round trips and missing/duplicate headers.

### F23 — P2: the edit gate blocks the research needed to clear it

**Reproduced.** `hooks/edit-gate.mjs:35–38` reads `file_path` only to check presence, then ignores the target. Under hard-block, editing `research/DISCOVERY.md` to resolve a failure is denied. Default ask mode repeatedly requests exceptions for legitimate research edits. The registered matcher also covers a specific runtime's tools, not every possible write mechanism; file-path-less payloads allow immediately.

Suggestion: allow clearly scoped research work, evaluate the correct project root, and test the actual runtime's tools. Treat prompt instructions, tool-hook enforcement, and commit enforcement as different controls. Do not enable hard-block globally before proving the research-repair path remains usable.

### F24 — P2: source classification assigns primary status to lookalike hosts

**Reproduced.** `core.mjs:117` uses an unanchored `github.com` pattern: `https://notgithub.com.example.org/fake` is labeled P. Any `docs.*` host and any preferred domain can also receive P without establishing ownership of the specific fact. The latter is a heuristic/design limitation, whereas the lookalike-host match is a concrete bug.

Suggestion: anchor hostname checks and separate discovery preference from source authority. Store the organization, ownership rationale, and claim-specific authority; treat automatic labels as provisional until reviewed.

### F25 — P2: cost and failure accounting do not provide a run budget

**Code-traced; thin-page behavior covered by an existing passing test.** `maxScrapes` caps fetch attempts, not searches/maps or total credits. Searches occur before full URL validation and before acquiring the collection lock. Thin successful responses under 200 characters are discarded and logged as failures, losing paid-for content and forcing another request on retry. Cache reuse is logged as a failed scrape in `.usage.jsonl` because only `result === 'scraped'` gets `ok:true`. There is no coordinator-level throttling, Retry-After handling, retry/backoff policy, or persisted per-job resume queue; the external CLI may have behavior this review did not inspect.

Suggestion: separate run spend from scrape count, account for each operation/attempt, preserve thin content with its quality grade, record cache hits accurately, and make retries bounded and classified. Validate a complete plan before spending anything. A scheduler is justified after the basic Windows path works, not as a substitute for fixing it.

### F26 — P2: the secret scanner's clean result omits common secret files

**Reproduced.** `doctor.mjs:50` skips every dotfile except `.env`, including `.env.local` and credential-bearing hidden JSONL logs. A synthetic matching key in `.env.local` produced no hits. The scanner only recognizes a Firecrawl-shaped pattern and has file-count/size limits. The actual `.gitignore` also lacks `.env` and `.firecrawl/` rules.

Suggestion: describe the scan's coverage honestly, include supported environment-file variants and relevant logs, scan for additional credential types when configured, redact credentials from stored request URLs, and add ignore protection. No real secret was found or exposed by these probes.

### F27 — P1: the line-ending recovery advice can delete uncommitted research

**Code-traced; deliberately not executed.** `handoff.mjs:56–67` recommends recursively deleting the entire research directory before checking it out again. Uncommitted or untracked evidence, notes, decisions, and logs can be lost, and this current folder has no Git metadata from which to restore them.

Suggestion: require an actual repository, inspect tracked/untracked state, take a backup, and restore only verified affected tracked files. A diagnostic should never print a broad destructive remedy without its preservation prerequisites.

## What the current PASS does not prove

These are quality/control limitations, including deliberate existing policies, rather than claims that every one is an implementation regression.

1. **Evidence relevance.** E-04's Finding concerns `/doctor` availability, while U-2 asks where Freebuff discovers skills. E-06's Finding is an age/eligibility clause, while U-4 asks about the intended use. The raw pages may contain useful sections, but the synthesized claims do not express the answers the brief needs. `claimOf()` promotes the first linked page's generic Finding into the answer.
2. **Correct target runtime.** U-2 closes a Freebuff-specific question using Claude Code documentation. This session's available skill catalog explicitly includes `.agents/skills`; that does not establish the full discovery contract, but it contradicts treating the Claude roots as exhaustive evidence for this runtime. A local discovery/enforcement acceptance check is still needed. A configured `.claude` hook is not that check.
3. **Independent support.** The generated brief asserts agreement of two independent sources without verifying independence or requiring two references. One full capture can satisfy the completeness rule for a multi-source unknown without covering all its subclaims.
4. **Coverage and deferral.** Missing/blank maps may pass with a warning. KNOWN-UNKNOWN requires only a sufficiently long text cell. One failed fetch anywhere suppresses attempted-research warnings for all deferred questions (`checks.mjs:397`). No relationship between that failed URL and each deferred question is required.
5. **Schema and freshness research.** MAP dismisses schema stability by saying there is no extraction layer, yet both adapters parse changing payloads/HTML and `finding.mjs` extracts claims. Generic 30-day local cache and 180-day gate defaults do not establish freshness requirements for every fact. Negative/future ages also remain “fresh”; row dates are not checked against the capture date as strictly as capture-vs-ledger timestamps.
6. **Authenticity.** The ledger establishes internal hash consistency. It is not a signature from the origin, cannot prove semantic truth, and a writer with full corpus access can recompute an entire chain. No signed external checkpoint was found. Use it for provenance consistency within a stated trust boundary.
7. **Operational readiness.** Doctor checks registration, credentials, files, and ledger shape, not a completed collection-to-reviewed-brief exercise. Comparing a hook path to the currently running kit copy makes source/deployed diagnostics disagree. Missing `.git` is not reported as a project blocker. Transport selection labels an installed-but-unauthenticated CLI “anonymous” without proving anonymous collection works.
8. **Historical documents.** The current MAP still says this machine has no key, despite authenticated status. Existing audits can be stale because of F06. Instructions include stray trailing quotation marks in several example commands. README says failed fetches never enter the ledger, while the collector explicitly writes `op: fail`. These discrepancies make resumption less reliable.

## Additional boundaries and previously reported issues

- **Capture symlinks:** the earlier report's blanket overwrite claim needs narrowing. `uniqueRawName()` skips an existing path when `existsSync()` is true. Dangling symlinks, symlinked directories, and check/write races remain concerns because the final write does not require exclusive creation or validate the destination type. No Windows symlink exploit was executed here.
- **Repair wording:** `--repair` can report “nothing to do” when a ledger is broken. The command then still evaluates preflight; this is misleading repair feedback, not proof that the entire command returns success. The repair function also does not independently validate the intact prefix before dropping a partial last line.
- **Async harness:** the main await fix works in its regression tests. A timed-out test is not cancelled and later cases can overlap its side effects, as ADR-0021 acknowledges. Sync tests can block the event loop beyond its watchdog. Consider subprocess isolation if tests gain persistent asynchronous work. These are separate from the 16 observed failures.
- **Partial-write recovery:** capture, ledger, evidence, and source rows are separate writes, so a crash between them can leave an orphan or an unindexed capture. Cache reuse does not verify ledger membership or repair missing rows. Decompose's failure handling and the append-tail defect worsen recovery. No full power-loss campaign was run.
- **HTTP limits:** the keyless adapter clears its abort timer after receiving headers, before reading the full body; its parent process eventually supplies a coarser timeout. Content type and response size are not usefully constrained for PDFs/binary or extremely large pages. It can access loopback/private endpoints; decide explicitly whether that is an intended collector capability before treating untrusted plans as safe inputs.
- **No-verification override records:** a pre-commit hook cannot log an invocation Git bypasses with `--no-verify`. No separate observer was found. Claims that every such bypass is automatically recorded are too strong.
- **Audit grouping:** output versions can advance independently per scope; removed subtopics remain in the manifest and may remain in a later bundle. Concurrent audit writers and slug collisions were not stress-tested. These deserve dedicated fixtures after the reproduced audit defects are fixed.

## Suggestions for a more reliable machine

These are proposed priorities and acceptance criteria, not changes made during this review. Existing ADRs should be superseded explicitly when a chosen proposal changes their policy.

| Priority | Proposal | Acceptance criterion |
|---|---|---|
| First | Isolate tests and repair Windows collection invocation. | Tests cannot address real user/config paths; real search/map/scrape argument paths work on Windows, including spaces, Unicode, encoded URLs, and query strings, without shell execution. |
| First | Protect reviewed briefs, audit freshness, manifest paths, and ledger recovery. | Re-running generators never loses authored text; changed conclusions generate new correct-version artifacts; manifests cannot escape; interrupted collection resumes without corrupting prior evidence. |
| Next | Make collection a single durable writer with recoverable jobs. | Two collectors, slow requests, process termination, and restart preserve unique IDs and valid evidence links; no accidental duplicate spend on completed work. |

For transport design, a verified Node entry point minimizes architecture changes but retains CLI-version coupling. A direct official API adapter removes the `.cmd` layer but requires explicit credential handling and API error/schema tests. Moving execution into WSL/Linux is an operational alternative, but it creates another environment to configure and does not fix brief/audit/provenance defects. Choose based on the desired supported platform; a full rewrite is not necessary.

For persistence, first make the current file format transactional enough for one writer. If durable concurrency and resumable queues become requirements, a small transactional metadata store with immutable raw files is a reasonable later option. Keep Markdown as the review/export surface. Avoid adding a database merely to conceal unresolved claim semantics.

## Suggestions for higher-quality research

The most valuable improvement is an explicit claim-review process. More pages or more agents will not repair an irrelevant claim linked to a valid hash.

1. **Store a claim separately from a page.** Give each claim a question ID, a precise answer, supporting evidence IDs, a section/paragraph locator or short supporting excerpt, applicable version/date/region, confidence, limitations, and reviewer status. One page may support several claims; one claim may need several pages.
2. **Separate fact, inference, and decision.** Mark directly documented facts distinctly from conclusions inferred from them. A recommendation must state its reasoning and what observation would change it.
3. **Review authority per claim.** A vendor is authoritative about its API; that does not make it independent evidence for its product's comparative performance. A docs-shaped hostname is not an authority test.
4. **Seek disconfirming evidence.** For important conclusions, deliberately search for exceptions, version differences, changelogs, deprecations, regional restrictions, and contradictory primary sources. Record unresolved contradictions instead of generating “none.” Multiple URLs on one publisher's site do not automatically provide independence.
5. **Give critical unknowns a stop condition.** An unavailable must-have output or unverified blocking assumption should lead to a clear no-go or bounded experiment. KNOWN-UNKNOWN should carry impact, owner, verification step, and a rule about whether building may proceed.
6. **Use fact-specific freshness.** Recheck volatile prices, limits, availability, and versions close to handoff; stable protocol definitions can use longer intervals. Preserve original source dates and upstream-cache metadata alongside retrieval time. Firecrawl's documentation explicitly distinguishes a fresh fetch from proof of current real-world state. [Freshness guidance](https://docs.firecrawl.dev/features/scrape#freshness-and-item-status).
7. **Require a reviewed handoff.** Every blocker answered or explicitly accepted; every important answer supported by the cited section; coverage dispositions reviewed; contradictions resolved or labeled; no TODO decision; clear first build step and no-go conditions. Make the brief sufficient for a builder without implying that review eliminates every future research need.
8. **Evaluate outputs against a small benchmark.** Use representative tasks with known expected answers: one API integration, one changing pricing/limits question, one unavailable-data case, and one conflict between sources. Measure answer correctness, citation support, omitted constraints, outdated claims, reviewer corrections, credits per accepted claim, and whether a builder can act on the brief. Set targets after measuring a baseline.

I would prioritize reliable invocation and preservation first, then claim relevance and handoff review. Tightening every warning into a failure immediately would block work on the current legacy corpus without fixing the underlying reasoning or transport problems.
